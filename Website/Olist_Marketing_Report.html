Case Study: Olist Brazilian Marketplace (100k+ Transactions)

1. Introduction & Problem Statement

In the highly competitive e-commerce landscape, customer acquisition costs (CAC) are rising. For a marketplace like Olist, the primary challenge is not just finding new customers, but maximizing the Lifetime Value (CLV) of existing ones.

The Problem: Raw transactional data is "silent." Without a structured analytical framework, the business cannot distinguish between a one-time buyer and a loyal brand advocate. This leads to inefficient marketing spend, where "At-Risk" customers are ignored and "VIPs" are under-served. We need to transform 100,000 rows of fragmented data into a clear Retention Strategy.

2. Methodology & Data Dictionary

To solve this, we architected a relational data environment by merging 9 separate datasets. Below are the primary tables engineered for this analysis:

  • A. The Recency Table (Temporal Engine)
    Source: orders + customers
    Key Elements: order_purchase_timestamp, order_status, customer_unique_id.
    Feature Engineering: Created a Snapshot Date (Max Date + 5 days) to calculate Days_since_last_order.
    Purpose: Measures the "freshness" of the customer relationship and identifies churn patterns.
  • B. The VIP Table (Premium Customer Tracker)
    Source: Aggregated orders merged with financial core
    Key Elements: customer_unique_id, frequency, payment_value.
    Purpose: Quantifies customer engagement and spend. This allows us to definitively recognize our highest value premium tier based on both how often they purchase and their total monetary footprint.
  • C. The Monetary Table (Financial Core)
    Source: order_payments + customers + geolocation
    Key Elements: payment_value, payment_type, lat/lng coordinates.
    Purpose: Tracks total revenue contribution and geographic wealth distribution across Brazil.
  • D. The Product Affinity Table (Segment Context)
    Source: order_items + products + translation_lookup
    Key Elements: product_id, product_category_name_english, price.
    Purpose: Maps high-value segments to specific product categories to enable Targeted Lifecycle Marketing.

3. Project Aim & Objectives

The ultimate goal of this project is to build a Tableau-powered Marketing Command Center. To achieve this, our data preparation focused on three strategic aims:

  1. Unified RFM Scoring: Merge the R, F, and M metrics into a single "Golden Record" per customer. This allows for Unsupervised Learning (K-Means Clustering) to automatically group customers into personas (e.g., "Champions," "Can't Lose Them," "Hibernating").
  2. Geospatial Revenue Mapping: Use payment values and coordinates to visualize the "Economic Heart" of the marketplace, identifying which Brazilian states require more logistical or marketing investment.
  3. Actionable Strategy Development: Use the Product Affinity data to design a 1-page "Recovery Plan" for At-Risk VIPs, specifically suggesting categories they are likely to buy based on their historical behavior.

Step 1: Building the Recency Table

This script establishes our temporal baseline. First, we merge the customer base with the orders database. Why? To link physical purchases to unique consumer IDs. We then explicitly drop all data where order_status is not 'delivered'. Including canceled or failed orders artificially skews recency metrics, implying a successful retail interaction that never materialized. Finally, we calculate a constant 'Snapshot Date' (adding 5 days to the max purchase date in the entire dataset) to mathematically compute exactly how many days have elapsed since every individual's last successful transaction.

import pandas as pd
import numpy as np

# STEP 1: Load the base datasets
orders = pd.read_csv('olist_orders_dataset.csv')
customers = pd.read_csv('olist_customers_dataset.csv')

# STEP 2: Merge the tables together mapped perfectly on 'customer_id' 
merged = pd.merge(orders, customers, on='customer_id', how='left')

# STEP 2.5: Consistent Filtering! 
# We cleanly filter out failed, invoiced, or canceled orders right here at the root level!
merged = merged[merged['order_status'] == 'delivered'].copy()

# STEP 3: Handle the Math for Time Tracking 
# We explicitly convert our main timestamp string column natively into pandas DateTime formatting.
merged['order_purchase_timestamp'] = pd.to_datetime(merged['order_purchase_timestamp'])

# We manually identify the exact absolute latest purchase date in the entire universe of this dataset.
latest_purchase_date = merged['order_purchase_timestamp'].max()

# Using python timedelta logic, we systematically add exactly 5 forward bounds (days).
# This establishes our firm, stable analytical 'Snapshot Date'.
snapshot_date = latest_purchase_date + pd.Timedelta(days=5)

# STEP 4: Calculate the explicit Recency Core Value
# We literally subtract the unique customer's specific timestamp away from our fixed forward snapshot date.
# We then isolate specifically the underlying `.dt.days` count map.
merged['Days_since_last_order'] = (snapshot_date - merged['order_purchase_timestamp']).dt.days

# STEP 5: Store the modified database completely silently to disk
merged.to_csv('Recency Table.csv', index=False)

Step 2: Building the Frequency Table

Here, we mathematically isolate recurring premium customers. Why? Frequency is the ultimate marker for brand loyalty. We strictly mandate that the dataset only registers 'delivered' items—again, to prevent inflated loyalty tracking from refunded returns. By leveraging a strict .nunique() isolation specifically on actual `order_id` values, we guarantee that multiple items bought within one single checkout basket aren't incorrectly counting as separate visits.

import pandas as pd

# STEP 1: Load the combined data
# We read the previously created 'Recency Table.csv' into a DataFrame.
recency_df = pd.read_csv('Recency Table.csv')

# STEP 1.5: Filter out non-delivered orders
# We strictly evaluate frequency metrics ONLY on successfully 'delivered' orders.
recency_df = recency_df[recency_df['order_status'] == 'delivered'].copy()

# STEP 2: Calculate Frequency (How many distinct orders did each customer place?)
# Let's break down exactly what this single line of code is doing:
# 1. `.groupby('customer_unique_id')`: It gathers all rows belonging to the same actual person into groups.
# 2. `['order_id']`: From those groups, it focuses only on the column containing the underlying order IDs.
# 3. `.nunique()`: It asks, "How many uniquely different order IDs are inside this group?" 
#                  (This is crucial! If a customer bought 3 products in a single checkout, they will have 3 rows 
#                  sharing the exact same order_id. `nunique` ensures we just count that as 1 distinct order.)
# 4. `.reset_index()`: pandas defaults to making the grouped column (customer_unique_id) an "index" label. 
#                      This turns it back into a standard, neat 2-column DataFrame holding customer_unique_id and their order_id counts.
frequency_df = recency_df.groupby('customer_unique_id')['order_id'].nunique().reset_index()

# STEP 3: Rename the column to be descriptive
# After the step above, the column holding our counts is confusingly still named 'order_id'.
# We rename it to 'frequency' so we know this column represents the count of total orders.
frequency_df.rename(columns={'order_id': 'frequency'}, inplace=True)

# STEP 4: Sort the data
# We sort the DataFrame based on the 'frequency' column in descending order (highest to lowest).
# This helps us easily see our most loyal/frequent customers at the very top of the table.
frequency_df = frequency_df.sort_values(by='frequency', ascending=False)

# STEP 5: Save our final metric table
# We export this new tiny table (which just maps a unique customer to their total order count) to a CSV file.
# `index=False` makes sure pandas doesn't write out the row numbers (0, 1, 2, 3...) to the file.
frequency_df.to_csv('Frequency Table.csv', index=False)

Step 3: Building the Monetary Table

We combine sheer financial payment totals with customer IDs to track CLV (Customer Lifetime Value). Why? The highest-frequency buyer doesn't matter if their cart values are zero. We meticulously dropped tracking columns like order_approved_at, estimated_delivery_date, and order_status because they offer zero relevant value to monetary modeling and just bloat the pipeline. We also safely executed a drop_duplicates() on the 1M+ row geolocation map before merging. Why? To prevent catastrophic 'row-multiplication' where multiple identical zip-code coordinates artificially duplicate a customer's total payment spend.

import pandas as pd

# STEP 1: Basic Merge (Orders + Customers)
orders = pd.read_csv('olist_orders_dataset.csv')
customers = pd.read_csv('olist_customers_dataset.csv')

# Join the datasets perfectly keeping all orders
df = pd.merge(orders, customers, on='customer_id', how='left')

# FILTER: Keep only 'delivered' orders, then drop irrelevant columns
df = df[df['order_status'] == 'delivered'].copy()
df.drop(columns=[
    'customer_id', 
    'order_status', 
    'order_approved_at',
    'order_delivered_carrier_date', 
    'order_delivered_customer_date', 
    'order_estimated_delivery_date'
], inplace=True)

# STEP 2: Geolocation Data
geo = pd.read_csv('olist_geolocation_dataset.csv')

# CRITICAL: The geolocation dataset has many rows for the exact same zip code (over 1M rows!).
# If we do a raw join, it will multiply our orders massively. 
# We must drop duplicated zip codes so there is exactly 1 geographical point per zip code.
geo_unique = geo.drop_duplicates(subset=['geolocation_zip_code_prefix'])

# Left join using customer zip code -> geolocation zip code
df = pd.merge(
    df,
    geo_unique,
    left_on='customer_zip_code_prefix',
    right_on='geolocation_zip_code_prefix',
    how='left'
)

# Drop the redundant city and state columns as requested
df.drop(columns=['geolocation_city', 'geolocation_state'], inplace=True)

# STEP 3: Payment Data
payments = pd.read_csv('olist_order_payments_dataset.csv')

# Left join on order_id. We keep everything from payments.
# Note: If an order was paid in multiple installments (e.g. card + voucher), 
# this WILL increase the row count because each payment will have its own row!
df = pd.merge(df, payments, on='order_id', how='left')

# Save the master monetary table
output_filename = 'Monetary Table.csv'
df.to_csv(output_filename, index=False)

Step 4: Building the Product Affinity Table

This links English product categories back to our core buyers. Why? We forcefully drop columns like product_height_cm, product_weight_g, and shipping bounds. A marketing command center doesn't care about the physical cubic volume or warehouse weight of a product; it exclusively requires the contextual categorization of what the user likes to buy. Trimming this fat yields a highly optimized blueprint ready for content-targeting engines.

import pandas as pd

# STEP 1: Load the Base Datasets
# We start by bringing our two foundational files directly into memory: the list of all orders and the list of customers.
orders = pd.read_csv('olist_orders_dataset.csv')
customers = pd.read_csv('olist_customers_dataset.csv')

# STEP 2: Customers-Orders Connection
# We securely attach all customer details (like zip codes and unique IDs) onto the master orders list.
# The 'left join' ensures we perfectly match them based on their exact shared 'customer_id' without losing any orders.
df = pd.merge(orders, customers, on='customer_id', how='left')

# STEP 3: Add the Item Details per order
# The 'order_items' file holds the physical items bought inside each order (since 1 checkout can have multiple items).
# We join this onto our master table using the 'order_id' so every order now explicitly contains its individual item rows.
order_items = pd.read_csv('olist_order_items_dataset.csv')
df = pd.merge(df, order_items, on='order_id', how='left')

# STEP 4: Add specific Product Details
# Now that we know WHAT items were bought, we bring in the master products dataset.
# We join it using 'product_id' so we can confidently attach specific descriptions and features directly to the physical items.
products = pd.read_csv('olist_products_dataset_merged.csv')
df = pd.merge(df, products, on='product_id', how='left')

# STEP 5: Filter the Universe to only Successful Deliveries
# We logically slice the massive table so it only ever keeps completely successful transactions.
# Any failed, invoiced, processing, or canceled orders are completely removed here.
df = df[df['order_status'] == 'delivered'].copy()

# STEP 6: Clean Out the Clutter
# To keep memory light and analytics focused, we isolate every single irrelevant column. 
# This includes the now-redundant status string, internal logistical dates, and physical boxing dimensions.
columns_to_drop = [
    'customer_id',
    'order_status',
    'order_purchase_timestamp',
    'order_approved_at',
    'order_delivered_customer_date',
    'order_estimated_delivery_date',
    'shipping_limit_date',
    'product_category_name',
    'product_name_lenght',
    'product_description_lenght',
    'product_photos_qty',
    'product_weight_g',
    'product_length_cm',  # Dropping length
    'product_height_cm',  # Dropping height
    'product_width_cm'    # Dropping width
]

# We natively execute the drop command right here via pandas. 
# `errors='ignore'` is a safety net: it ensures the script silently continues even if a given column was naturally already missing.
df.drop(columns=columns_to_drop, inplace=True, errors='ignore')

# STEP 7: Safe Storage Output
# Finally, we silently export the completely polished, distilled tabular data directly back onto the hard drive.
df.to_csv('Product Affinity Table.csv', index=False)

Step 5: Synthesizing the VIP Target List

Finally, we synthesize the two heaviest RFM weights (Frequency and Monetary) into a master schema. Why? By enforcing a strict inner merge across customer_unique_id, we surgically prune any fragmented customers who survived earlier filter cracks (e.g., users who placed an order but failed payment authorization). The resulting VIP table guarantees flawless, 100% delivered, high-value consumer data explicitly ready for complex machine-learning clustering algorithms to target.

import pandas as pd

# STEP 1: Load the Aggregates
# We silently import the two pre-calculated metrics datasets.
freq_df = pd.read_csv('Frequency Table.csv')
mvip_df = pd.read_csv('M_VIP.csv')

# STEP 2: Merge 
# We explicitly merge them together on the shared identifier.
# We are intentionally using an 'inner' join. Why? The Frequency table currently holds 96,096 people, 
# but the Monetary table intentionally holds only 93,358. 
# This perfectly logical drop occurred because we aggressively filtered the Monetary pipeline 
# to absolutely only include rows marked completely as 'delivered', whereas the early Frequency 
# pipeline counted everyone (including people whose items got canceled, failed processing or lost).
# An inner join gracefully auto-drops those 2,738 non-delivered customers so our resulting VIP 
# table strictly reflects genuinely successful orders with actual payments mapped to them.
vip_df = pd.merge(freq_df, mvip_df, on='customer_unique_id', how='inner')

# STEP 3: Export 
# Saving the fully combined list out to your hard drive entirely silently.
vip_df.to_csv('VIP Table.csv', index=False)
